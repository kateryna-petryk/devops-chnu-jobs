# ЛР5 – Аналіз потенційних місць відмови системи (ЧНУ Jobs)

## 1. Короткий опис системи

Проєкт **ЧНУ Jobs** – це веб-платформа для студентів ЧНУ (Чорнівецький національний університет), на якій:

- студенти (роль `STUDENT`) можуть реєструватися, переглядати вакансії та практики, подавати заявки на стажування/роботу;
- представники компаній (роль `FIRMA`) можуть створювати вакансії, переглядати відгуки студентів, змінювати статус заявок, закривати вакансії;
- є роль `ADMIN` для майбутнього розширення (адмінка).

Технології:
- **Backend**: Flask (Python 3.11)
- **База даних**: PostgreSQL
- **Запуск**: локально через Docker Compose (контейнери `app` і `db`) + sandbox/production середовища на Render.com
- **Основні сценарії**: реєстрація, логін, перегляд вакансій, подання заявки, перегляд заявок компанією.

---

## 2. Потенційні місця відмови

### 2.1. База даних PostgreSQL

**Ризики:**
- Перевищення максимальної кількості підключень (`max_connections`).
- Повільні запити при великій кількості даних (SELECT із JOIN на кількох таблицях).
- Блокування таблиць при одночасних записах (INSERT в `applications`, UPDATE `jobs`).
- Падіння БД → вся система стає недоступною (неможливо залогінитись, подати заявку тощо).

**Умови відмови:**
- Високе одночасне навантаження (велика кількість студентів, які одночасно відкривають список вакансій та подають заявки).
- Некоректно налаштований пул підключень або обмеження на ресурсах (free-tier база на Render).

---

### 2.2. Веб-додаток (Flask)

**Ризики:**
- Один процес Flask (development server) обслуговує обмежену кількість одночасних запитів.
- Багато одночасних запитів на “важкі” сторінки (наприклад, `/jobs`, `/firma/applications`) → збільшення часу відповіді.
- Наявність блокуючих операцій (наприклад, bcrypt-хешування пароля) при великій кількості реєстрацій/логінів.

**Умови:**
- Велика кількість одночасних логінів (студенти перед дедлайном подачі заявок).
- Масове використання сторінок, де є JOINи по декількох таблицях (список заявок, список вакансій).

---

### 2.3. Взаємодія app ↔ DB

**Ризики:**
- Невірно налаштований `DATABASE_URL` або середовище (особливо на sandbox/production).
- Таймаути підключення до БД.
- Немає ретраїв або навпаки – занадто агресивні ретраї, що затримують старт сервера.

**Умови:**
- Нестабільна мережа між web-сервісом та БД (в хмарі).
- Різкі спайки навантаження.

---

### 2.4. Мережа та хостинг

**Ризики:**
- Ліміти безкоштовного тарифу (Render free tier): “sleep” сервісу при бездіяльності, холодний старт.
- Обмеження CPU/RAM → повільні відповіді при піках навантаження.

**Умови:**
- Багато одночасних студентів/компаній (спайкове навантаження).
- Погана мережа з боку користувача (може не критично для бекенду, але впливає на UX).

---

### 2.5. Логін / Реєстрація та безпека

**Ризики:**
- Bcrypt має певну "вартість" (cost factor). При великій кількості логінів процесор може бути перевантажений.
- Можливий brute-force на логін (велика кількість невдалих спроб).

**Умови:**
- Масові логіни/реєстрації в піковий момент (наприклад, коли відкриваються нові вакансії).
- Атакуючий навмисно бомбить `/login`.

---

## 3. Критичні сценарії для тестів навантаження

1. **Багато студентів одночасно відкривають список вакансій** (`GET /jobs`).
2. **Багато студентів одночасно подають заявки** (`POST /jobs/<id>/apply`).
3. **Багато компаній одночасно переглядають заявки** (`GET /firma/applications`).
4. Масові **логіни студентів та фірм** (`POST /login`).
5. Комбінований сценарій: паралельно:
   - частина користувачів логіниться,
   - частина переглядає вакансії,
   - частина подає заявки,
   - частина компаній дивиться заявки та змінює статус.
