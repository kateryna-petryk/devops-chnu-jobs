# ЛР5 – План тестування навантаження (ЧНУ Jobs)

## 1. Мета тестування

Перевірити, як система **ЧНУ Jobs** поводиться при підвищеному навантаженні:

- чи залишається доступною;
- чи не з’являються помилки 5xx;
- як змінюється час відповіді у критичних сценаріях;
- при якому навантаженні система перестає відповідати прийнятно (точка відмови).

---

## 2. Інструменти

Для тестування навантаження можна використати:

- **Locust** (Python-based, зручно, бо проєкт теж на Python);
- або **k6** (JavaScript-скрипти, консольний інструмент).

У плані будемо орієнтуватися на **Locust**, але фактично можна використати будь-який інструмент.

---

## 3. Цільові показники (SLO/SLA)

Попередньо задаємо такі орієнтири:

- Середній час відповіді для основних ендпоінтів: **до 500 мс** при нормальному навантаженні.
- Допустимий час відповіді при піковому навантаженні: **до 2 секунд**.
- Рівень помилок (HTTP 5xx) – не більше **1%** від загальної кількості запитів під час тесту.
- Система повинна витримувати умовно:
  - 50 одночасних “користувачів” (virtual users) на sandbox;
  - 100+ одночасних користувачів на production (у майбутньому).

---

## 4. Сценарії навантаження

### 4.1. Smoke test (перевірка, що тестове середовище взагалі працює)

**Мета:** пересвідчитись, що середовище готове до навантаження.

- 5 віртуальних користувачів.
- Триває 1–2 хвилини.
- Сценарій: 
  - відкриття `/` (landing);
  - відкриття `/jobs`;
  - відкриття `/login` та `/register`.

Очікування: 0 помилок 5xx, час відповіді < 500 мс.

---

### 4.2. Load test – список вакансій (читання)

**Мета:** перевірити, як система поводиться при масовому перегляді вакансій.

- 50–100 одночасних користувачів.
- Тривалість: 10–15 хвилин.
- Сценарій:
  1. Користувач відкриває `/jobs`.
  2. Відкриває деякі детальні сторінки `/jobs/<id>`.
  3. Повторює цикл.

Метрики: час відповіді `/jobs`, кількість помилок.

---

### 4.3. Load test – подання заявок (запис)

**Мета:** перевірити масову подачу заявок студентами.

Передумови:

- Є кілька активних вакансій у БД.
- Є тестові акаунти студентів.

Сценарій (для кожного віртуального користувача-студента):

1. Логін (`POST /login`).
2. Відкриття `/jobs`.
3. Вибір вакансії та `GET /jobs/<id>`.
4. Надсилання заявки: `POST /jobs/<id>/apply`.

Параметри:

- 20–50 одночасних користувачів.
- Тривалість: 10 хвилин.

---

### 4.4. Load test – компанія переглядає заявки

Сценарій:

1. Логін як `FIRMA`.
2. Відкриття `/firma/applications`.
3. Періодичне оновлення сторінки, зміна статусів для окремих заявок (`POST /firma/applications/<id>/status`).

---

### 4.5. Stress test

**Мета:** зрозуміти, на якому рівні навантаження система “ламається”.

- Поступове збільшення кількості користувачів: 10 → 20 → 50 → 100 → 150.
- Сценарій: суміш:
  - частина користувачів логіниться;
  - частина переглядає `/jobs`;
  - частина подає заявки;
  - частина компаній переглядає заявки.

Фіксуємо:

- при якому рівні навантаження:
  - з'являються масові помилки 5xx;
  - різко росте час відповіді;
  - БД перестає відповідати.

---

## 5. Метрики, які збираємо

1. **Response time** (середній, 95-й, 99-й перцентил).
2. **Throughput** (запитів/сек).
3. **Помилки HTTP 4xx, 5xx**.
4. Для локальних тестів через Docker – бажано подивитися:
   - CPU та RAM контейнера `app`;
   - CPU та RAM контейнера `db`.

---

## 6. Умови проведення тестів

- Тестування проводиться на **sandbox-середовищі** (branch `develop`) на Render.com.
- Параметри бази даних відповідають minimal free-tier конфігурації.
- Використовуються тестові дані користувачів (тестові акаунти STUDENT/FIRMA).

---

## 7. Критерії успішності

Тест вважається успішним, якщо:

- при запланованому навантаженні (наприклад, 50 одночасних користувачів) система:
  - не падає (немає масових 5xx);
  - більшість запитів мають час відповіді менше 1 секунди;
- відсутні “вузькі місця”, які повністю блокують виконання критичних бізнес-сценаріїв (логін, перегляд вакансій, подання заявки).
